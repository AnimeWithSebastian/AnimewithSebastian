WHY THIS FILE EXISTS (credit reduction — creative quality unchanged)
The old system fired TWO scheduled runs ~1 hour apart. Each reloaded large split
runtimes, ran a full 8-search stack, launched a model, drafted a long audit-heavy
email, validated, sent and logged. That is ~2x the model launches, ~2x the research
sweeps and ~2x the file loading per day.

This ONE run produces BOTH next-day Shorts packages (MORNING + EVENING) in a single
model context, with ONE shared market research sweep, ONE model launch, a compact
actionable email per slot, a deterministic preflight validator (no model revision
for mechanical issues), and a single atomic dual-event log append. Weekly analytics
(cron 2bb28991) is UNCHANGED and still runs on its own Sunday cadence.

CREATIVE STANDARDS ARE NOT RELAXED. Every law that governed the morning/evening
runs still governs both packages here. This file REFERENCES the durable law prose in
hero_or_villain_master_laws_final.txt and laws/ instead of re-pasting it every day —
enforcement is unchanged; only the daily token load is reduced.

PENDING-BATCH CHECK (Law #166, added 2026-08-13, part of the Law #164 approval
gate; CARVE-OUT + PARSING RULE ADDED 2026-08-15, docs/KNOWN_ISSUES.md F37/F38)

  *** HOW TO READ A PENDING BATCH'S STATUS — DO THIS FIRST ***
  PARSE state.json AND READ THE "status" FIELD. Do NOT substring-grep the file
  for the awaiting-approval token. A completed batch's state.json legitimately
  CONTAINS that token inside explanatory prose (its own correction note explains
  what its status used to be), so a grep-based check re-blocks on a batch that
  is actually finished. This is not hypothetical — it was hit while fixing F38
  on batch 32e0fcb9. Only the value of the top-level "status" field counts.

  A pending batch BLOCKS today's run only if BOTH are true:
    (a) its state.json "status" field is exactly "AWAITING_APPROVAL", AND
    (b) it has no confirmed send — i.e. no row for its batch_id in
        cron_tracking/sent_scripts_events.jsonl, and the top-level
        cron_tracking/daily_combined/state.json does not record that batch_id
        as status="success" / emails_sent=true.

  A batch whose status is terminal ("sent") is NOT a blocker. Since 2026-08-15
  tools/append_send_batch.py flips the per-batch pending copy to "sent"
  automatically on a successful send (F38 fix, fail-safe: it only ever flips on
  success), so in normal operation a completed batch self-clears.

  CORRECTION-BATCH CARVE-OUT (F37): a batch carrying a "corrects_batch_id" field
  is a correction of an earlier batch, not a fresh daily backlog item. If such a
  batch satisfies (a) but FAILS (b) — i.e. it reads awaiting-approval yet its
  packages are demonstrably already sent — that is the F38 stale-state bug, not a
  real backlog. Do NOT skip the day for it. Instead: flip that batch's per-batch
  state.json to status="sent" (recording why, and preserving every STEP 6 field
  including any held_packages), note it in the run log, and CONTINUE normally.
  IMPORTANT: a batch reaching terminal status NEVER means a separately held
  package was resolved. Batch 32e0fcb9 is the worked example — Link Click sent,
  Slime still held under Law #165 / F36, and closing the batch did not close F36.

STEP 3.5 — LENGTH SELECTION (Law #138 Stage 1/2 — content-driven, not fixed)
================================================================================
Edit length is now an open per-content judgment call in [20,180]s (Law #138,
Stage 1 rebuild 7851d85 / Stage 2 62dbc56) — there is no fixed 30s default and no
format_type/series gate. The validator only enforces the outer [20,180]s bound and
the CTA/VO-band math against whatever capcut_target_sec is actually set; the BAND
an idea should target is a drafting decision, made HERE, right after idea selection
and before drafting begins, using the real content of the two ideas just picked in
STEP 3.

The gate is the number of independently source-verified beats the topic actually
has — NOT a length picked first and padded to fit. Count the distinct, separately-
sourced factual/narrative beats the verified research (STEP 2/3) actually supports
for this idea before choosing a band:
  - SINGLE-FACT / QUICK-TAKE (1 verified beat) -> 20-30s. One clean claim, one
    reaction. Reserve this band for ideas that are genuinely single-fact AND
    where YouTube-only distribution is acceptable for that package — this band
    produces content that cannot earn TikTok Creator Rewards (TikTok requires
    videos to be at least one minute long to qualify for any Creator Rewards
    payout, per TikTok's own Creator Rewards Program support page; sub-60s
    videos earn $0 regardless of views). This is no longer the default
    assumption; it is a deliberate exception, and the package's
    length_rationale must say so explicitly (e.g. "YouTube-only — single
    verified beat, does not support 60s+").
  - MULTI-BEAT ARGUMENT (2-3 verified beats building one throughline) -> 45-75s.
    Unless the package is explicitly marked YouTube-only (see above), TikTok
    Creator Rewards eligibility is the DEFAULT assumption for this channel —
    TikTok is the platform with confirmed real traction. TikTok pays $0 on any
    video under 60 seconds regardless of views, full stop (TikTok Support,
    confirmed). That means "somewhere in 45-75s" is NOT sufficient by itself:
    for a TikTok-eligible package, the resolved capcut_target_sec must be
    >=60s specifically, not merely inside this band's outer range.
    At idea selection, once an idea's verified beat count places it in this
    band, resolve it one of two ways — do not let it land silently at 45-59s:
      (a) If the idea's verified beats genuinely support pushing the resolved
          length to 60s+ within this same band, do so. Using room the real
          beats justify is not padding — the anti-padding rule below still
          governs how much content actually fills that time; it just means
          don't round down to 50-55s when the sourced material could
          legitimately fill 60+.
      (b) If the verified beats genuinely do NOT support 60s+ — the idea is
          real 2-3-beat content but thin enough that stretching to 60s would
          require padding — mark the package YouTube-only in length_rationale,
          the same explicit carve-out used for the 20-30s band, and resolve
          capcut_target_sec anywhere in 45-59s that honestly fits the content.
          Do not resolve at 45-59s while treating the package as if it were
          still TikTok-eligible; a package is either >=60s or explicitly
          YouTube-only — there is no silent middle state.
  - FULL CHARACTER DEEP-DIVE (multiple verified beats tracing one character/arc
    across time) -> 90-150s.
  - MULTI-CLAIM EXPLAINER (several independently-verified claims that don't reduce
    to one throughline — e.g. a news roundup or multi-thread update) -> up to 180s.
Pick the SHORTEST band that genuinely fits the verified beat count for this idea,
with 60s+ (reached via the MULTI-BEAT ARGUMENT band or higher) as the practical
floor for ordinary, TikTok-eligible content — do not default upward past what the
verified beat count supports, but do not default down into 20-30s, or stop short
at 45-59s, out of habit either. A single-fact idea forced into a 90s band will
pad; a genuine explainer squeezed into 30s will drop sourced beats. Set
capcut_target_sec to a specific numeric value inside the chosen band (not just the
band's edges) based on how much verified content the idea actually carries.
Record the chosen band and the beat count that justified it in the manifest per
package (e.g. a `length_rationale` note) so the choice is auditable, not just a
number that appears with no reasoning attached. Every package's length_rationale
must make its status legible: either the specific verified-beat justification for
a resolved length >=60s, or an explicit YouTube-only mark with the reason 60s+
wasn't genuinely supported. Never resolve a length in the 45-59s dead zone without
the YouTube-only mark attached — that combination gets neither the honesty of the
20-30s exception nor actual TikTok eligibility, and defeats the purpose of this
change.

  8. REDUNDANT SENTENCE CHECK (Law #149 point 1 -- NO REDUNDANT SENTENCES): confirm
     no VO sentence merely restates a prior sentence in different words. Every

     is never a valid reason to keep a sentence that adds nothing new -- expand with
     a genuinely new, sourced detail instead, per Law #149 point 1 directly.
  9. AI-SLOP PATTERN CHECK (new, 2026-07-26 -- distinct from point 8; catches
     hollow-sounding phrasing even when no sentence literally repeats another).
     Confirm the VO contains NONE of the following seven patterns. For each,
     if found, REWRITE the line to a concrete, sourced claim before returning
     the manifest -- do not attest this check true with an instance present.
       a. HOLLOW SIGNIFICANCE STATEMENT -- a sentence that asserts importance
          without stating what the importance IS.
          Reject: "This moment changes everything about how we see him."
          Accept: "This is the first time the manga confirms he lied to Zoro's face."
       b. POETIC RESTATEMENT AS NEW INSIGHT -- a single sentence that sounds
          like a discovery but only rephrases the prior sentence's own claim
          in more evocative language (narrower than point 8: this catches ONE
          sentence performing insight with no new fact, not just literal
          repetition across two sentences).
          Reject: "It's not just a fight. It's a reckoning."
          Accept: "He's not fighting Gaban to win. He's fighting him to earn
          the key Gaban was never going to hand over for free."
       c. RULE-OF-THREE PADDING -- three parallel words/phrases stacked for
          rhythm where the sources support at most one or two of them.
          Reject: "Bold. Brutal. Unforgettable."
          Accept: (state the one specific, sourced claim the rhythm was
          standing in for, or cut the line).
       d. GENERIC RHETORICAL SCAFFOLDING PHRASES -- banned regardless of
          context: "here's the thing," "but that's not all," "and it gets
          better," "here's where it gets interesting," "little did we know."
          These add zero information and exist only to fake momentum.
          Reject: "But here's the thing: Gaban was never planning to lose."
          Accept: "Gaban was never planning to lose."
       e. STACKED INTENSIFIERS WITH NO ATTACHED FACT -- intensifying
          adjectives/adverbs ("absolutely," "completely," "utterly,"
          "shockingly," "insanely") used to carry a sentence's weight instead
          of a specific fact.
          Reject: "This is an absolutely shocking twist."
          Accept: "This flips the fight's entire premise: Gaban was the one
          being tested, not Luffy."
       f. THE "IT'S NOT JUST X, IT'S Y" FORMULA -- banned as a fixed
          construction regardless of what fills X and Y.
          Reject: "It's not just a key. It's a verdict."
          Accept: state the verdict directly as its own sourced claim.
       g. GENERIC URGENCY FRAMING WITH NO SPECIFIC CONSEQUENCE -- urgency
          language ("you need to see this," "this changes everything," "you
          won't believe") with no stated, specific consequence attached.
          Reject: "You need to see how this fight ends."
          Accept: "The fight ends with Gaban handing over the exact thing
          Luffy spent the whole episode trying to take by force."
     This check is a self-audit judgment call like point 8 -- Law #149's
     point 2 (Specificity Over Gesture) and Law #54's banned-hedge-phrase
     mechanism are the closest existing precedent, but neither law names
     these seven forms or supplies reject/accept pairs for them; this point
     closes that naming gap rather than duplicating either law.

     GRAMMAR CORRECTNESS IS NOT PART OF THIS CHECK (Law #149 point 7, added
     2026-08-06): this point 9 check is scoped to the seven hollow-phrasing
     patterns above -- it is NOT a formality/properness filter, and basic
     grammar (subject-verb agreement, correct verb forms after perception verbs
     like "see"/"hear"/"watch" + object + bare infinitive, e.g. "we see him get
     his moment," not "gets") must never be flagged or softened under this
     check regardless of how casual the VO's register is. A genuine grammar
     error (subject-verb agreement, wrong verb form) is always a mistake to fix
     outright -- correct it on its own correctness grounds, separately from this
     point's seven patterns, never by rewriting toward a more formal register.
     Conversely, casual/repetitive/informal phrasing that is grammatically sound
     must NOT be "corrected toward properness" under this or any other point --
     this law's entire purpose is sounding like a real person, not sounding
     polished. Real example (Gachiakuta, 2026-08-06): "the preview show us
     three new enemies" and "we also see Enjin gets his moment" were initially
     flagged as too formal/proper, but the actual defects were subject-verb
     agreement ("show" -> "shows") and verb form after "see" ("gets" -> "get")
     -- grammar mistakes independent of register, not AI-slop or formality
     issues. Full text: Law #149 point 7 in hero_or_villain_master_laws_final.txt
     and laws/law_149_vo_writing_craft.md.
  9.5 ISOLATION TEST (new, 2026-08-05, Law #144 point 4): for hook_onscreen_text
     and hook_line, isolate them from the rest of the VO and ask: does a reasonable
     viewer, seeing ONLY the on-screen text and the spoken first line -- nothing
     else -- walk away with an accurate understanding of what was actually
     confirmed or happened? Most Shorts viewers decide whether to keep watching
     within the first 1-2 seconds, before any later disambiguation can land, so a
     hook that is technically defensible by the end of a fully-watched VO can still
     be misleading to that majority. FAIL if the hook implies something stronger,
     different, or more definitive than what the full VO ultimately delivers --
     even if a later sentence explicitly corrects or caveats it; a correction
     arriving after the misleading impression has landed does not cure the
     failure. Worked example (real, caught 2026-08-05): "Jujutsu Kaisen Season 4's
     Date Just Got Real" implied a release date was confirmed; the actual content
     was a convention/event date (Juju Fest, Aug 29-30) with an explicit "No
     release date yet" five sentences later -- FAILED and was rewritten to lead
     with the event ("Juju Fest") instead of the ambiguous word "date". Second
     worked example (real, caught 2026-08-06): "This 'easy' battle wasn't the
     real fight" (Tanya S2 Ep4) implied a bigger combat payoff via the word
     "fight"; the actual content was a political peace-deal rejection, no second
     battle -- FAILED and rewritten to "They won the war. Then they voted against
     peace." GENERAL PATTERN (both instances): a single word's most likely
     isolated reading ("date" -> confirmed date; "fight" -> combat) promised
     something the content didn't deliver -- not a rule about dates or combat
     language specifically. Check a hook's key word against its single most
     likely reading, not just a defensible one. Like point
     9, this is a self-audit judgment call, not validator-enforced -- if FAIL,
